# Agent instructions — knowledge_database

## Project overview

This repository is a knowledge base stored as plain Markdown files, with indexes designed to be navigated by an LLM agent through a dedicated skill, plus the Python tooling that keeps it up to date. The database *is* the Markdown files — there is no server or query engine in the read path — and the indexes alongside them exist so an agent can find the relevant document, and the relevant part of it, in as few reads as possible instead of loading the corpus into context. The other half is ingestion: Python utilities that take a source document (PDF is the common case; Markdown, DOCX, and EPUB are also expected, and the list is open-ended), normalize it into the Markdown corpus, and refresh the indexes so the addition is discoverable. See `README.md` for the fuller statement of purpose and design constraints.

Three consequences shape almost every task here:

- **The indexes are a contract, not an implementation detail.** The navigating skill depends on their structure, so changing an index format breaks every agent that reads it. Treat index-format changes as `risk-high` and reindex the whole corpus in the same change.
- **Ingestion and indexing are one operation.** A document added without reindexing is invisible to the agent, which is a silent failure rather than a loud one — the corpus looks fine and the knowledge is simply unreachable. Never ship an ingestion path that can add without indexing.
- **Agent-first over human-first.** Where index design trades human browsing convenience for agent navigation efficiency, agent navigation wins.

Nothing beyond this document and the pipeline configuration is built yet: the corpus layout, the index format, and the ingestion tools are all still to be designed. Rows below marked `TODO` are unresolved for that reason, not overlooked — fill each one in as the corresponding code lands, and prefer a stale `TODO` to an invented rule.

## Validation commands

Run these in order before opening a PR or pushing a hand-worked branch. Any non-zero exit is a gate failure.

```bash
ruff check .
ruff format --check .
pytest
```

⚠️ **These are not yet installed.** They were configured as the intended Python gate for a repository that had no toolchain at setup time, not detected from a manifest. Until `ruff` and `pytest` are present and a test suite exists, expect the gate to fail on a missing executable. Add the toolchain and a `pyproject.toml` in the first substantive PR, or change `validation.commands` in `.ai/agentic.config.json` to match the stack the project actually adopts — and update this section and `SDLC.md` in the same change.

## Pointers

- `SDLC.md` — the ticket-to-merge process, label state machine, and claim protocol.
- `.ai/agentic.config.json` — the machine-readable configuration every `om-*` skill reads.
- `.ai/trackers/github.md` — the authoritative definition of every tracker operation; the repo's copy overrides the shipped one.
- `.ai/browsers/agent-browser.md` — the browser-automation contract.
- `.ai/skills/<skill-name>/SKILL.md` — repo-local extension of an installed skill, for repo-specific rules. Local rules win on repo specifics but can never relax the installed skill's safety or quality rules.
- `CODE_REVIEW.md` — **not generated.** When added at the repo root it is picked up automatically by `om-code-review` and therefore `om-auto-review-pr`.
- `BACKWARD_COMPATIBILITY.md` — **not generated, and now clearly warranted.** It defines the protected contract surfaces that review and implementation skills check changes against, and this project has an obvious one: **the index format**, consumed by the navigating skill and by any agent reading the corpus. The ingestion CLI's commands and flags are a second. Write this file as soon as the index format is decided — it is the mechanism that makes review skills flag a silent breaking change instead of approving it.
